    What a StaticSet guarantees, and what it does not¤

    A static Pod is a Pod that a node owns rather than the cluster: kubelet reads a manifest from a directory on its own filesystem and starts it. Kubernetes finds out about it afterwards, as a mirror Pod it cannot edit and must not schedule. That is the whole point — the workload keeps running, and comes back after a reboot, without the control plane being reachable.

    The guarantee¤

    After an installation has been acknowledged, kubelet restarts the last installed revision following a host reboot, without Kubernetes API access.

    "Restarts" here means kubelet starts the containers again from the manifest it finds. Whether they come up depends on the same things it always does, which is why the next section exists.

    What that depends on¤

    The guarantee is about the manifest, not about the application. It holds only while these are true on the node:

    • Images are present locally. A container whose image is missing will not start without a registry. spec.offline.imageProvisioning decides whether the operator simply reports that images are externally provisioned, or refuses to publish a revision until they are confirmed present.
    • The container runtime and networking are up. A static Pod uses the node's runtime and CNI like any other Pod; kubelet restoring a manifest does not restore a broken runtime.
    • Storage is available. Anything the workload mounts from the node must still be there. Kubernetes-backed storage (a persistentVolumeClaim) is rejected outright, because attaching a volume needs the API server.
    • The application's own dependencies are reachable. Data stores, peers, secrets it fetches at runtime: none of that is the operator's promise.

    What it is not¤

    • Not arbitrary Pod compatibility. Only a conservative, validated subset of the Pod API is compiled; see the translation reference for the exact list. A field the operator cannot represent faithfully is rejected, never dropped, because a static Pod that silently lost a field would start, look healthy, and behave differently from the template it came from.
    • Not a replica count. spec.replicas counts placements, not running copies of the workload. A placement that is relocated can briefly leave two nodes' worth of offline workloads in existence, and a Surge rollout deliberately leaves two revisions on one node for a moment; see placement and capacity.
    • Not an exact replica guarantee during a partition. A partitioned node keeps serving whatever it last installed. Nothing the operator can do from the control plane changes that, and pretending otherwise would be the worst outcome.
    • Not a configuration manager. The operator copies configuration content onto the node at install time. A ConfigMap that changes in the cluster becomes a new revision; a ConfigMap that changes and is then never reconciled does not.

    Why a scheduler probe and a node manager¤

    The alternative — writing manifests from the controller — would require the controller to have a filesystem relationship with every node, which is both a large privilege and a large failure domain. The other alternative — letting a per-node agent pick its own work — would throw away the cluster's scheduler, which is the only thing that knows about capacity, affinity, taints and topology.

    So the work is split along that line:

    • the controller decides what should exist and reports what it observes. It mounts nothing from the host and runs unprivileged. To learn where a workload should run, it creates a scheduling probe — a ReplicaSet or DaemonSet whose Pods carry the workload's resources and the StaticSet's placement rules, and which run under a runtime class no node can start. The scheduler places them; nothing executes;
    • a manager runs once per node, as a DaemonSet, and serves every StaticSet whose placement names its node, in every namespace. It writes, updates and removes the manifests on that node and reports what it did, so a replacement adopts the placement its predecessor left behind rather than creating a second one.

    The cost is that installation is asynchronous: a StaticSet is not installed until the node's manager says so, which is why the status distinguishes installed state from observed health instead of collapsing both into "ready".
